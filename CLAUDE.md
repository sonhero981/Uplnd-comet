# UpLnD — Spec & Workflow Repo

> Specs, change tracking and Comet state for UpLnD (UpBase's LMS). This repo holds no application code:
> code lives in the sibling repos below, and every change is designed and tracked here.

---

## Workflow: Comet Classic (OpenSpec + Superpowers)

```
open → design → build → verify → archive
```

- `/comet-open` → `/comet-design` → `/comet-build` → `/comet-verify` → `/comet-archive`; lighter presets `/comet-hotfix`, `/comet-tweak`.
- **Start here: `/comet-start`.** It reads the approved PRDs from the PO repo (`../uplnd_po_workflow/intents/INDEX.md`; override with env `PRD_REPO`), shows which PRDs already have changes, then offers a menu: continue a change, new feature from a PRD (`/comet-open`), hotfix, or light tweak, and hands off to that skill. `node scripts/prd-status.mjs` prints the same list in the terminal (`--json`, `--no-fetch`).
  - A change is tied to a PRD by a line `PRD: LMS-F001` right after the title of its `proposal.md` (several codes comma-separated; omitted for a hotfix/tweak with no PRD). `openspec/config.yaml` has a rule so `/comet-open` writes it.
  - The list only holds PRDs already approved in the PO repo's `INDEX.md` (generated by `po-tools.py index`); a PRD the PO has not indexed yet does not appear. The script runs `git fetch` on the PO repo to warn when it is behind, and never pulls or edits it.
  - **Technical design.** The Tech PIC's design lives in the PO repo (`intents/<intent>/inception/tech-design/`: `tech-design.md`, and for FE `fe-technical-design.md`); it is not copied here. `/comet-start` shows its state per PRD: `ready`, `template` (stage 2.43 creates `tech-design.md` from the template with only the frontmatter filled, so a file that still equals the template counts as missing) or `missing`. When a PRD chosen for a new feature has none, it asks whether to draft one, use the existing `fe-technical-design.md`, skip, or stop. The change's `design.md` opens with `Tech design: <path> @ <PO repo commit>` and links to it instead of repeating it (rule in `openspec/config.yaml`).
  - **Drafting a technical design: `comet-tech-design` skill.** It writes `tech-design.md` in the PO repo from that repo's own template, the approved PRD and the real code of the sibling repos, as a **draft** for the Tech PIC. Before writing, `node scripts/po-tech-design.mjs prepare <intent>` creates the branch `feature/<intent>-tech-design` in the PO repo from the branch it is on (stops if the PO repo has uncommitted changes, or is on another intent's tech-design branch unless `--base <branch>`). The skill never commits, pushes, ticks a gate or edits any other PO file; the Tech PIC reviews, commits and pushes. It does not run the `/tech` AI-DLC stages of `upbase-specs` (domain, contract, units…), which exist only in that repo.
  - `comet-start`, `comet-tech-design`, `comet-codekb`, `comet-jira`, `comet-assign` and `comet-next` are custom skills of this repo, not part of Comet; if `comet update` ever removes them, restore them from git.
- `auto_transition: false` (`.comet/config.yaml`): Comet does **not** start the next phase by itself; nothing starts without the user's choice.
- **Next-step menu (`comet-next`).** When `/comet-open`, `/comet-design`, `/comet-build`, `/comet-verify`, `/comet-archive`, `/comet-hotfix`, `/comet-tweak` or `/comet-assign` finishes and its manual handoff would end with "run `/comet-…` yourself", do **not** end the turn on that command text: load the `comet-next` skill for the change instead. It reads `node scripts/next-step.mjs` and asks with a select box (the next phase, assign, refresh codekb, back to `/comet-start`, stop), then loads the skill the user picked. This keeps the manual handoff (the user still decides) and only replaces typing a command with picking an option; it overrides the phase skills' wording "end this invocation without another confirmation question" for that final prompt only. It never advances a phase itself. **One exception, `/comet-open`:** when it finishes, load `comet-jira` for the change first (whether it was started by `/comet-start` or typed directly), so the change's Jira stories and sub-tasks are recorded at creation; `comet-jira` then hands over to `comet-next`. For a batch of changes opened one after another, do this after each one. Skip it only if the user said not to sync with Jira.
- Phase guard: read `.comet.yaml` `phase` of the change before any operation. No implementation writes in `open`, `design`, `verify`, `archive`.
- Settings: `artifact_layout: legacy` (OpenSpec at `openspec/`, Superpowers docs at `docs/superpowers/`), `memory.learning: false`.
- **Artifact language is Vietnamese**, even though `classic.language` stays `en` (Comet 0.5.2 accepts only `en` or `zh-CN`; `vi` makes `comet doctor` fail). When a Comet skill says to use the configured artifact language, write `proposal.md`, `design.md`, `tasks.md` and spec prose in Vietnamese instead, keeping technical terms, code identifiers, paths and Jira keys in English. Never translate what tools parse: template section headings, `## ADDED/MODIFIED/REMOVED Requirements`, `### Requirement:`, `#### Scenario:`, `SHALL`/`MUST`, `WHEN`/`THEN`. Same rule is in `openspec/config.yaml` `context:`. Reply to the user in Vietnamese.
- Setup on a new machine: `npm install -g @rpamis/comet`, then `comet init --yes --workflow classic --platform claude --scope project --skip-existing --codegraph skip --language en` and `comet doctor`. `.claude/settings.local.json` is generated per machine and is not committed. Also install and index CodeGraph (section "CodeGraph"). On Windows run `init` from a path whose drive letter is uppercase (`E:\...`): Comet 0.5.2 compares the hook path case-sensitively, so a lowercase `e:\...` makes `comet doctor` report "managed Hook missing".

## Layout

```
openspec/
  products.yaml                         # product → module → capability → repos reference list (documentation only, no tool reads it)
  changes/<module>-<name>/              # active changes (name never contains a repo); archived copies get a YYYY-MM-DD- prefix under changes/archive/
    .comet.yaml                         # Comet phase tracker
    specs/<product>/<module>/<capability>/spec.md   # delta specs mirror the main-spec path
  specs/<product>/<module>/<capability>/spec.md     # archived main specs, grouped by product, not by repo
docs/superpowers/{specs,plans,reports}/ # Design Docs, build plans, verification reports
docs/codekb/<repo>/                     # code knowledge base: 9 AWS AI-DLC Reverse Engineering files per sibling repo (+ areas/)
```

Naming: a change is `<module>-<name>` — module slug plus a feature name, e.g. `user-account-manager-relations`. **The name never contains a repo.** One change can span several repos; the only place the repo split is recorded is `tasks.md`: groups headed `## N. [<repo>] <title>`, in build order `lms-package → lms-be → ops-fe → lms-fe`. The `[<repo>]` tag is what the list view reads. `proposal.md` and `design.md` have no required per-repo sections. No OpenSpec or Comet document prescribes this split; it is this repo's own convention, kept to one rule on purpose.

The rule is in `openspec/config.yaml` `rules:`, so tasks generated by `/comet-open` follow it.

**Assigning.** After `/comet-open` writes `tasks.md`, run `/comet-assign` (`/comet-start` asks for it at the end of `/comet-open`): it asks who takes each repo, suggesting people from `openspec/team.yaml` (seeded from the repo owners of `upbase-specs`; add the rest of the team there), and records the answer in `openspec/changes/<change>/assignees.yaml` through `node scripts/assignees.mjs` (`show`, `set --repo|--group`, `unset`, `team`). The file holds a default person per repo and optional overrides per group number. It is kept out of `tasks.md` on purpose: Comet tracks `tasks.md` by task ids and hashes, and an extra line there can read as drift. No Jira issue is created. Rerun `/comet-assign` to reassign.

**Jira.** Jira is the source of truth for the PO's stories, sub-tasks, assignees and status (`jira.upbase.asia`, project `UPLND`); a PRD has many stories and a story has `[BE]`/`[FE]` sub-tasks labelled with the PRD code and the repo. A change covers several stories (the 6 changes of `LMS-F002` follow the PRD units, not the 15 stories), so `/comet-jira` (right after `/comet-open`, or on its own) records, in `openspec/changes/<change>/jira.yaml`, which stories the change covers and which sub-task(s) each `## N. [<repo>]` group does (`node scripts/jira-link.mjs show|stories|group|unlink|covered`). It reads Jira through the Jira MCP, fills `assignees.yaml` from the sub-tasks' assignees, lists stories no change covers (`/comet-jira coverage`), and **only after asking** creates missing sub-tasks and moves finished ones to `Done`. It never edits `tasks.md`, `proposal.md`, a story, estimates or Story Points (a Jira automation sets a story's points to the sum of its sub-tasks' points and has overwritten the PO's). The `/dev-feature` flow of `ops-fe` and `lms-fe` (which also creates sub-tasks) is not used here.

**Listing changes by repo.** `node scripts/changes.mjs` prints every active change with its phase and, indented under it, each repo with that repo's task progress and assignee (`→ name`, or `(chưa giao)`); `node scripts/changes.mjs --repo ops-fe` keeps only changes that touch `ops-fe`. For the plain Comet views use `comet status` or `openspec list`.

**Specs and archive.** The delta spec of a change lives at the same nested path as its main spec (`specs/uplnd/<module>/<capability>/spec.md`), so `openspec archive` merges it into `openspec/specs/<same path>`. Unlike `product-ups`, this repo has no flatten/nest hook: OpenSpec 1.14.1 was tested to create and modify nested specs directly (`openspec archive` and `openspec validate --specs`). Not yet exercised through `comet archive`; check `openspec/specs/` after the first real archive. If a nested delta is ever skipped ("No deltas found"), reintroduce the flatten/nest hook from commit `451dd75` (`scripts/openspec-specs.mjs`, `scripts/hooks/comet-archive-specs.mjs`, `.claude/settings.json`).

On archive, add any new capability to `openspec/products.yaml` and stage the new spec paths with the archive commit.

## Sibling Repos

Build order for a change that spans repos: `lms-package` → `lms-be` → `ops-fe` → `lms-fe`.

| Repo | Code path | Stack | Conventions to read first |
|---|---|---|---|
| `lms-package` | `../lms-package/packages/` | shared `@upbase-tech/*`, pnpm + turbo | `README.md` (no `.claude/CLAUDE.md` on `main`) |
| `lms-be` | `../lms-be/apps/` | NestJS · Nx · TypeORM · Kafka | `CLAUDE.md` → `openspec/README.md` |
| `ops-fe` | `../ops-fe/{apps,features,libs}/` | Vite · React Router · pnpm monorepo | `.claude/CLAUDE.md`, `.claude/rules/` |
| `lms-fe` | `../lms-fe/apps/` | Next.js 14 (lms-pro, lms-test, lms-zoom) | `.claude/CLAUDE.md`, `.claude/rules/` |

When exploring or designing a change, navigate to the relevant repo and load its own conventions file before designing.

### Code knowledge base (codekb)

`docs/codekb/<repo>/` is the shared, verified picture of each sibling repo's code, built by **`/comet-codekb`** (the AWS AI-DLC stage 2.1 Reverse Engineering, same 9 files as `upbase-specs/domain/codekb/`: `business-overview`, `architecture`, `code-structure`, `api-documentation`, `component-inventory`, `technology-stack`, `dependencies`, `code-quality-assessment`, `reverse-engineering-timestamp`, plus optional `areas/<area>.md`). It records `origin/staging` (`origin/main` for `lms-package`), not whatever branch a sibling repo happens to be checked out on. The repo's own conventions are not copied into it; its files link to them.

- **Use it as context.** Before `/comet-open`, `/comet-design`, `/comet-tech-design` and before dispatching build work, read `docs/codekb/<repo>/architecture.md` and `code-structure.md` of every repo the change touches, plus the matching `areas/*.md`, then verify the specific lines you rely on in the code. Cite what you take from it as `repo:path:line`. It narrows where to look; it does not replace reading the code you change.
- **Check freshness.** `node scripts/codekb-status.mjs` prints per repo: `CURRENT`, `STALE` (commits touched the scanned paths since the scan), `NO_STORE`, `INCOMPLETE`, `UNKNOWN_SCOPE` or `UNVERIFIED`. `/comet-start` shows it. On anything but `CURRENT`, say so and treat the codekb for that repo as a hint, not as fact; offer `/comet-codekb`.
- **Feature knowledge has no file of its own.** What a feature does is `openspec/specs/uplnd/<module>/<capability>/spec.md` (merged in at `/comet-archive`); why and how it was built is the archived change under `openspec/changes/archive/<date>-<change>/` (`proposal.md`, `design.md`, `tasks.md`). For a change that touches an existing feature, read its spec first and the archived `design.md` of earlier changes on the same module.
- **Refresh.** After `/comet-archive` of a change that touched code, run `/comet-codekb refresh <change>` (focused scan of the areas the change touched). `/comet-codekb` never edits a sibling repo; it writes only under `docs/codekb/`.

### CodeGraph (live code lookup)

Each sibling repo has a local CodeGraph index (`<repo>/.codegraph/`: symbols and call graph). It complements the codekb: the codekb is the checked, explained picture of `origin/staging` and can be STALE; CodeGraph answers "where is X, who calls X, what breaks if I change X" on the checked-out working tree, about a second after an edit.

- **Use it before `grep`/`Read`** when locating or understanding code in a sibling repo. MCP tools `codegraph_explore`, `codegraph_node`, `codegraph_callers`, `codegraph_search` (registered by `.mcp.json`), or the shell: `codegraph explore "<symbols or question>" -p ../<repo>`, `codegraph callers <symbol> -p ../<repo>`, `codegraph impact <symbol> -p ../<repo>`. Always pass the repo path: this repo has no index of its own. Use `grep`/`Read` for what it does not index (config, docs, SQL, migrations).
- **Name symbols, not topics.** Tried on `lms-package`: `query` and `callers` by symbol name were exact; a broad question to `explore` came back off-target, partly because that repo commits a bundled build file (`packages/common-package/dist-local/editor.mjs`) that the index includes.
- **It reads the working tree, the codekb reads `origin/<base>`.** A sibling repo may sit on a feature branch, so the two can differ. Cite codekb facts to `origin/<base>`; check the line in the branch being edited.
- **Setup per machine:** `npm install -g @colbymchenry/codegraph`, then once per sibling repo `codegraph init -y ../<repo>` (it syncs by itself afterwards) and add `.codegraph/` to that repo's `.git/info/exclude`, because the sibling repos' own `.gitignore` does not list it and this repo does not edit them. The project-level `.mcp.json` here registers the MCP server. CodeGraph sends anonymous telemetry by default; `codegraph telemetry off` disables it.
- **Do not keep what `codegraph install` writes into `.claude/`** (`settings.json`, `CLAUDE.md`): the first is a Windows-only `codegraph.cmd` prompt hook, the second tells the agent to skip CodeGraph when the current repo has no `.codegraph/`, which is always the case at this repo's root. The committed `.claude/settings.json` of this repo holds only the design-system hooks (next section); do not merge CodeGraph's prompt hook into it.

### Design system (FE code)

The FE repos already carry their rules: `ops-fe` and `lms-fe` each have `.claude/rules/05-ui-and-styling.md` (`ops-fe`: "Reuse-first, BẮT BUỘC": grep before writing, `@ops/ui` wrapper before raw `antd`, never re-implement a component that has a wrapper, no hard-coded colours) and `.claude/inventory/01-ui.md` (the list of existing components, wrappers `UpBase*` / `HookForm*` in `lms-fe`). Duplicated components and ad-hoc styling come from not reading them, so this repo enforces them in three places:

- **Design:** for each group of `tasks.md` that touches `ops-fe` or `lms-fe`, `design.md` names the existing components to reuse and gives the reason for any new one (rule in `openspec/config.yaml`).
- **Build dispatch:** every implementer, reviewer and fix prompt sent into `ops-fe` or `lms-fe` must tell the subagent to read, after the repo's `CLAUDE.md`, `.claude/rules/05-ui-and-styling.md` and `.claude/inventory/01-ui.md`; to search for an existing component before writing any UI (`grep`, or `codegraph_search -p <repo path>`); to use the wrapper before raw `antd`; to create a component only when none fits and say why in the task note; and never to hard-code a colour.
- **Hooks that block:** `.claude/settings.json` runs `scripts/hooks/design-system-guard.mjs` on `PostToolUse` (`Edit|Write`), `Stop` and `SubagentStop`. A violation exits 2 with the reason and the agent must fix it before going on; never disable the hook to get past it. For `ops-fe` it runs the repo's own `scripts/design-system-hook.mjs` (ESLint `no-restricted-*` plus hard-coded colours in SCSS; the ESLint half needs `pnpm install` in `ops-fe`, without it only the SCSS check runs). `lms-fe` has its own `scripts/design-system-hook.mjs` and `.claude/settings.json` (same shape as `ops-fe`, so it also works when Claude is opened inside `lms-fe`); the guard runs it when the clone has it and otherwise runs the same checks itself (a copy kept in step by hand). It checks **added lines only** so legacy code is not flagged: a hard-coded colour, and a component imported straight from `antd` while `.claude/inventory/01-ui.md` lists `UpBase<Name>`. A justified exception goes on the same line as `// ds-allow: <reason>`. Those `lms-fe` files are uncommitted on its `main` until the `lms-fe` team reviews and merges them.

Limits: the `lms-fe` checks are a heuristic, not a lint; it is not verified that `PostToolUse` fires for files written inside a subagent, so `Stop` and `SubagentStop` are the backstop; the sibling clones sit on `main` while `ops-fe`'s `/ui-gate` command exists only on its `origin/staging`, so the rules can differ by branch.

**During `/comet-build`, none of this happens automatically.** Every implementer/reviewer/fix subagent runs in a fresh, isolated context and does not inherit this CLAUDE.md or the target repo's. So every dispatch prompt sent into a sibling repo — implementer, reviewer and fix agent alike — must explicitly instruct the subagent to read that repo's own `CLAUDE.md` (or the file in the last column) as its first step, then `docs/codekb/<repo>/architecture.md`, `code-structure.md` and the `areas/*.md` that match the task (give the absolute paths), and to use CodeGraph for code lookup with `-p <repo path>`.

Per `UP_BASE/HUONG-DAN-VAN-HANH.md`, `lms-be` is not on Comet yet (it keeps the legacy `/opsx` flow inside its own repo, because Comet 0.5.2 rejects repos with a root `*.lock` file). A change here that needs `lms-be` work is tracked in this repo; the `lms-be` implementation follows that repo's own flow.

## Comet Ambient Resume

In this repository, before starting work that may need code changes or investigation, pass the current user request to the read-only probe when a Comet workflow may already be active: `comet resume-probe . --stdin --json`.

- If the user explicitly invokes any Comet Skill through the host (for example, `@comet`, `/comet`, `@comet-native`, or `/comet-hotfix`), that explicit invocation takes precedence over this resume protocol; do not run the resume probe, and enter the invoked Skill directly.
- If the user explicitly invokes a non-Comet skill or slash command through the host, the task intent is already explicit in that invocation: do not run the resume probe, and execute the invoked skill directly.
- If you are already inside a Comet flow (including while waiting for the user to answer a question you asked in that flow), do not run the resume probe; treat replies such as option picks as continuation of the current change and proceed directly with the chosen option.
- Trust only the returned `workflow`, `skill`, and `entrySource`; project configuration or the no-config compatibility fallback alone selects them. Do not scan or switch to the other workflow.
- If the probe returns `auto_resume`, briefly state the selected active change and enter the permanent entry in `nextCommand`. Do not treat a state command as the resume entry or advance it blindly.
- If the probe returns `ask_user`, ask one short question and wait.
- If the current request did not explicitly invoke a Comet Skill and the probe returns `out_of_scope` or `none`, do not enter the Comet workflow.
- An `out_of_scope` or `none` result only means do not enter the Comet workflow for this new request; it never pauses or exits a Comet flow that is already in progress.
- If configuration or state is invalid and `nextCommand` is absent, stop and report the reason; do not guess another workflow.
- Never attach unrelated work merely because an active change exists. The Native entry inspects uncommitted work; the probe does not attribute it automatically.
